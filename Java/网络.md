### 键入网址到网页显示
1. 浏览器解析URL并生成HTTP消息
2. 客户端向本地DNS（通常由网络运营商自动分配）请求目标服务器的IP地址，当然如果本地有缓存可以直接查到
3. 拿到 IP 地址后，浏览器与服务器之间通过 **三次握手** 建立 TCP 连接。三次握手目的是**双方都保证双方都有发送和接收的能力**，一条 TCP 连接建立后，可以在上面连续发送多个 HTTP 请求。
4. 传输过程：路由器逐跳转发，知道下一站的 IP 地址之后（这一IP不会记录），接下来需要通过**ARP**协议根据 IP 地址查询 MAC 地址，并将查询的结果作为接收方 MAC 地址（ARP协议只在同一局域网内发送广播请求）。转发过程中目标IP地址作为最终目的地始终不变，每次转发MAC 头部都会被丢弃重装，（MAC 头部的作用就是将包送达路由器，其中的接收方 MAC 地址就是路由器端口的 MAC 地址）

## 应用层
- http协议：HTTP 是一个在计算机世界里专门在「两点」之间「传输」文字、图片、音频、视频等「超文本」数据的「约定和规范」，具体来说包括请求数据和响应数据的格式规范。HTTP协议区分了消息边界，解决了纯裸TCP的粘包问题。
### 请求协议和响应协议
1. 请求协议
	-  请求行：请求方式、资源路径、协议
	-  请求头：key-value形式，描述请求方的一些信息，如浏览器、数据格式等
	-  请求体：存放请求数据
2. 响应协议
	- 响应行：协议、状态码、描述
	- 响应头：key-value形式，描述响应内容的一些信息，如响应内容的类型、长度等
	- 响应体：存放响应数据
3. Web服务器
	- 对HTTP协议操作进行封装，简化Web程序开发
	- 在Web服务器上部署项目，可以直接对外提供网上浏览服务
	- SpringBoot一般会内置Web服务器

### 缓存技术
将请求-响应的数据缓存在本地，重复请求直接读取本地数据
- 强制缓存：第一次访问时，HTTP响应头会加上有效期字段，之后访问只要浏览器判断缓存没有过期，则使用本地缓存，主动权在浏览器
- 协商缓存：本地资源过期时，浏览器与客户端协商，服务器收到请求后进行比对，如果资源没有变化响应HTTP 304走缓存，如果资源变化了则返回最新资源
### 队头阻塞
- HTTP/1.x：队列前面的请求阻塞了后面的请求，即使后面的请求已经具备处理条件，也无法继续执行。
- HTTP/2：引入Stream，通过Stream ID区分属于哪个请求响应，每个HTTP消息被拆成了多个Frame，一个TCP连接可以并发传输多个Stream，如下图：
![[Pasted image 20260723202148.png]]
不同 Stream 的帧是可以乱序发送的，接收端可以通过 Stream ID 有序组装成 HTTP 消息，实现并发传输。然而，HTTP/2只解决了应用层的队头阻塞问题，在TCP层，一个 Frame 可以由多个 TCP 报文构成，仍然存在队头阻塞
- HTTP/3：将传输协议替换成UDP，且基于 UDP 协议在应用层实现了 QUIC 协议，QUIC 连接上的多个 Stream 之间并没有依赖，都是独立的，某个流发生丢包了，只会影响该流，其他流不受影响，从而解决传输层队头阻塞
### HTTPS（HTTP+SSL/TLS）
#### TLS协议建立流程（四次握手）
1. 客户端向服务器发起加密通信请求 Client Hello
2. 服务器收到客户端请求后，向客户端发出响应 Sever Hello，以及 Server Certificate 消息，该消息包含数字证书
3. 客户端收到服务器的回应之后，首先通过浏览器或者操作系统中的 CA 公钥，确认服务器的数字证书的真实性。如果证书没有问题，客户端会**从数字证书中取出服务器的公钥**，然后使用它加密报文，协商后续通信
4. 双方通过协商的加密算法，计算出本次通信的**会话秘钥**（对称加密），验证加密和解密没问题
至此，整个 TLS 的握手阶段全部结束。接下来，客户端与服务器进入加密通信，就完全是使用普通的HTTP 协议，只不过用「会话秘钥」加密内容。
#### 非对称加密算法
公钥和私钥一起生成，在数学上紧密相连。用公钥加密的数据，只能用配套的私钥解密；反之，用私钥加密的数据，也只能用配套的公钥解密。
- 公钥加密，私钥解密：目的是保证内容传输的安全
- 私钥加密，公钥解密：目的是保证消息不被冒充
非对称加密的主要用途是通过「私钥加密，公钥解密」的方式来确认消息的身份。为了解决漏洞“你怎么确定你拿到的公钥，真的属于你想通信的那个人，而不是黑客冒充的？”，引入解决方案：数字证书与权威机构（CA）

## 传输层
- TCP 是**面向连接的、可靠的、基于字节流**的传输层通信协议。
- TCP 四元组可以唯一的确定一个连接：源地址，源端口，目标地址，目标端口
### TCP连接建立——三次握手
三次握手过程如下：

使用三次握手的主要原因：
- 避免历史连接
- 同步双方初始序列号
- 避免资源浪费
### TCP连接断开——四次挥手
断开连接后主机中的「资源」将被释放，四次挥手的过程如下图：
![[Pasted image 20260729171750.png]]
双方都可以主动断开连接，**主动关闭连接的，才有 TIME_WAIT 状态**
使用四次挥手的原因：
- 关闭连接时，客户端向服务端发送 `FIN` 时，仅仅表示客户端不再发送数据了但是还能接收数据。
- 服务端收到客户端的 `FIN` 报文时，先回一个 `ACK` 应答报文，而服务端可能还有数据需要处理和发送，等服务端不再发送数据时，才发送 `FIN` 报文给客户端来表示同意现在关闭连接。
TIME_WAIT作用：
- 让最后一个ACK有补救机会：主动关闭方发送最后一个 ACK 后，如果这个 ACK 在网络中丢了，被动关闭方会以为自己的 FIN 没被确认，于是重发 FIN。主动关闭方还在 `TIME_WAIT` 里，就能再次回复 ACK；如果它已经进入 `CLOSED`，就可能回 RST，让对端感知为异常关闭或连接被重置。
- 防止旧连接的包混进新连接：TIME_WAIT 状态中可以正常接受之前的延迟数据，保证原来连接的数据包在网络中都自然消失，而不会混入下一次新建立的连接。
### TCP可靠传输

| 机制              | 触发条件                                   | 解决什么问题                      |
| --------------- | -------------------------------------- | --------------------------- |
| 超时重传（RTO）       | 超过 RTO 仍未收到 ACK                        | 兜底处理丢包，时间偏慢                 |
| 快速重传            | 收到 3 个 duplicate ACK，即连续确认同一个旧累计 ACK 号 | 不等超时，尽快重传疑似丢失的数据段，只能定位最早的缺口 |
| SACK （选择性确认）    | ACK 中携带已收到的数据区间                        | 告诉发送方哪些段已收到，只重传真正缺失的部分      |
| D-SACK（重复选择性确认） | SACK 中报告重复收到的数据段                       | 帮助识别误重传、ACK 丢失或网络乱序         |

## 网络层
### ARP协议（**Address Resolution Protocol**）
- ARP表：记录了某些其他网络设备的 IP 地址-MAC 地址映射关系，映射关系有生存周期，典型值为 20 分钟，超过该时间，该条目将被丢弃。
- ARP协议工作原理
	- 同一局域网内的MAC寻址
		1. 主机 A 检索自己的 ARP 表，如果发现 ARP 表中并无主机 B 的 IP 地址对应的映射条目，则将构造一个 ARP 查询分组，并将其广播到所在的局域网中。
		2. 主机 B 收到了查询分组之后，验证是对自己的问询，接着构造一个 ARP 响应分组，该分组的目的地只有一个——主机 A，发送给主机 A。
		3. 主机 A 终将收到主机 B 的响应分组，提取出该分组中的 IP 地址和 MAC 地址后，构造映射信息，加入到自己的 ARP 表中。
		4. ARP 协议是一个**广播问询，单播响应**协议，如下图：
		![[Pasted image 20260730211049.png]]
	- 不同局域网内的 MAC 寻址
			1. 主机 A 查询 ARP 表，期望寻找到目标路由器的本子网接口的 MAC 地址。目标路由器指的是，根据目的主机 B 的 IP 地址，分析出 B 所在的子网，能够把报文转发到 B 所在子网的那个路由器。直到主机 A 获取到目标接口的 MAC 地址，这个过程与同一局域网MAC寻址相同。
			2. 主机 A 将链路层帧以单播的方式发送给目标接口。目标接口接收到了主机 A 发过来的链路层帧，解析，根据目的 IP 地址，查询转发表，将该 IP 数据报转发到与主机 B 所在子网相连的接口上。
			3. 路由器接口查询 ARP 表，期望寻找到主机 B 的 MAC 地址。获得MAC地址后，路由器接口将对 IP 数据报重新封装成链路层帧，目标 MAC 地址为主机 B 的 MAC 地址，单播发送，直到目的地。

### NAT协议（**Network Address Translation**)
- 应用场景：内部网到外部网的地址转换。在一个子网（LAN）中，各主机拥有各自的私有IP，而在LAN外，在广域网（WAN）中，共用一个统一的公网IP，这在一定程度上也缓解了 IPv4 地址的分配压力。
- 细节：![[Pasted image 20260730215145.png]]
假设当前场景如上图。中间是一个路由器，它的右侧组织了一个 LAN，网络号为 `10.0.0/24`。LAN 侧接口的 IP 地址为 `10.0.0.4`，并且该子网内有至少三台主机，分别是 `10.0.0.1`、`10.0.0.2` 和 `10.0.0.3`。路由器的左侧连接的是 WAN，WAN 侧接口的 IP 地址为 `138.76.29.7`。当主机 `10.0.0.1`向外部发送请求时，随机指派一个端口，如 `3345`，作为本次请求的源端口号，`10.0.0.4` 即路由器的 LAN 接口收到 `10.0.0.1` 的请求。路由器将为该请求指派一个新的源端口号，如 `5001`，并将请求报文发送给 WAN 接口 `138.76.29.7`。同时，在 NAT 转换表中记录一条转换记录 **138.76.29.7:5001——10.0.0.1:3345**。在WAN中的请求源IP、端口和响应的目的IP、端口都是**138.76.29.7:5001**。
可以看到NAT协议的特点：
- NAT 协议通过对 WAN 屏蔽 LAN，有效地缓解了 IPv4 地址分配压力。
