## 索引[^1]

### 数据存储
InnoDB 的数据是按「数据页」为单位来读写的，数据页大小默认为16KB，也就是说数据库每次至少从磁盘读取16KB的内容到内存中，数据页之间通过双向链表连接，数据页中的记录按照「主键」顺序组成单向链表。
### B+树查询
InnoDB中的B+树的每个节点都是一个数据页[^7]，结构如下：
![[Pasted image 20260714113251.png]]
只有叶子节点存放数据，非叶子节点仅存放目录项作为索引。主键存储是有序的，定位记录时，通过二分法快速定位到包含该记录的页，之后在该页内进行二分法快速定位记录到所在的分组，最后在分组内进行遍历查找。
### 聚簇索引和二级索引
- 聚簇索引：叶子结点存放实际数据（数据行），只能有一个
- 二级索引：叶子结点存放主键值
如果某个查询语句使用了二级索引，但是查询的数据不是主键值，这时在二级索引找到主键值后，需要去聚簇索引中获得数据行，这个过程就叫作「回表」，也就是说要查两个 B+ 树才能查到数据。不过，当查询的数据是主键值时，因为只在二级索引就能查询到，不用再去聚簇索引查，这个过程就叫作「索引覆盖」，也就是只需要查一个 B+ 树就能找到数据。
### 联合索引
多个字段组合成一个索引，且字段存在先后顺序，使用联合索引时存在**最左匹配原则**。
例如联合索引(a, b, c)，是先按 a 排序，在 a 相同的情况再按 b 排序，在 b 相同的情况再按 c 排序。所以，**b 和 c 是全局无序，局部相对有序的**。
### 查询性能影响
树是存储在磁盘中的，树的高度等于每次查询数据时磁盘 IO 操作的次数，所以树的高度越高，就会影响查询性能。
- 二叉查找树 -> 极端情况退化为链表，时间复杂度从O(logn)降为O(n)
- 平衡二叉查找树 -> 作为二叉树，由于每个节点只能保存 2 个子节点，插入元素增多时树高度不可避免的增加，降低查询效率
- B树 -> 一个节点允许有M个子节点(M>2)，从而降低树的高度
- B+树 -> B树的升级，只有叶子节点存放实际数据，所有索引都会在叶子节点出现，叶子节点之间构成一个有序链表
## 事务
事务特性：原子性，一致性，隔离性，持久性
### MVCC（多版本并发控制）
- 记录中的隐藏字段：trix_id[^5]，roll_pointer[^6]
- undo log：实现事务回滚，保障事务原子性；协同read view实现MVCC
- read view：事务的版本快照，用来判断数据库中的某条记录哪个版本对当前事务可见
### 事务隔离级别
- 读未提交：可以读到未提交的事务
- 读提交：每次读取数据时都会生成一个新的Read View
- 可重复读：启动事务时生成一个Read View，然后整个事务期间都在用这个 Read View
- 串行化：所有事务串行执行

## 锁
### 行级锁加锁规则
**加锁的对象是索引，加锁的基本单位是 next-key lock（左开右闭）**，由 record lock 和 gap lock（左开右开） 组合而成
gap lock 的目的是防止幻读[^2]，主要以**幻读角度去分析加锁规则**
- 唯一索引等值查询
	1. 记录存在：next-key lock 退化为 record lock
	2. 记录不存在：next-key lock 退化为 gap lock
- 唯一索引范围查询
- 非唯一索引等值查询
	存在两个索引：主键索引和非唯一索引，对这两个索引都加锁，但是对主键索引加锁的时候，只有满足查询条件的记录才会对它们的主键索引加锁。
	1. 记录不存在：二级索引 next-key lock 退化为 gap lock，主键索引不加锁
	2. 记录存在：扫描，扫描到的二级记录加 next-key lock，第一个不符合条件的next-key lock 退化为 gap lock，符合条件的记录的主键索引加记录锁
- 非唯一索引范围查询：二级索引记录加 next-key lock
- 无索引查询：全表扫描，每一条记录的索引上都会加 next-key 锁，相当于锁住全表
### 死锁
- 死锁的必要条件：互斥、占有且等待、不可强占用、循环等待
- 解除死锁的策略：
	- 设置事务等待锁的超时时间
	- 开启主动死锁检测
- 死锁案例：在执行插入语句时，如果插入的记录在其他事务持有间隙锁[^3]范围内，插入语句就会被阻塞，因为插入语句在碰到间隙锁时，会生成一个插入意向锁[^4]，然后插入意向锁和间隙锁之间是互斥的关系。如果两个事务分别向对方持有的间隙锁范围内插入一条记录，而插入操作为了获取到插入意向锁，都在等待对方事务的间隙锁释放，于是就造成了循环等待，发生了死锁
## 日志
### undo log
回滚日志，记录更新前的数据。两大作用：  
- 事务回滚：事务处理过程出错后，利用 undo log 中的历史数据将数据恢复到事务开始之前的状态。
- MVCC：在执行快照读（普通 select 语句）的时候，会根据事务的Read View 里的信息，顺着 undo log 的版本链找到满足其可见性的记录。
### Buffer pool
Innodb 存储引擎设计了一个**缓冲池（_Buffer Pool_）**，来提高数据库的读写性能。
- 当读取数据时，如果数据存在于 Buffer Pool 中，客户端就会直接读取 Buffer Pool 中的数据，否则再去磁盘中读取。
- 当修改数据时，如果数据存在于 Buffer Pool中，那直接修改 Buffer Pool 中数据所在的页，然后将其页设置为脏页（该页的内存数据和磁盘上的数据已经不一致），为了减少磁盘 I/O，不会立即将脏页写入磁盘，后续由后台线程选择一个合适的时机将脏页写入到磁盘。
### redo log
为了防止断电导致内存上的脏页数据丢失，将页的修改以 redo log 的形式记录下来。在事务提交时，只要先将 redo log 持久化到磁盘即可，可以不需要等到将缓存在 Buffer Pool 里的脏页数据持久化到磁盘。两大作用：
- 实现事务的持久性，能够保证 MySQL 在任何时间段突然崩溃，重启后之前已提交的记录都不会丢失。
- 将写操作从「随机写」变成了「顺序写」，提升 MySQL 写入磁盘的性能。



[^1]: 索引的定义就是帮助存储引擎快速获取数据的一种数据结构，形象的说就是**索引是数据的目录**。

[^2]: 幻读是指当同一个查询在不同的时间产生不同的结果集时，事务中就会出现所谓的幻象问题。

[^3]: 间隙锁的目的是阻止其他事务插入该间隙，不同事务的间隙锁可以共存。

[^4]: 	用于并发插入操作，表明插入意图，使得多个插入同一索引间隙的事务无需等待，只要它们没有在间隙内的同一位置插入。与间隙锁冲突。

[^5]: 记录最近修改事务id

[^6]: 回滚指针，指向这条记录的上一个版本，配合undo log指向上一个版本

[^7]: 页是磁盘和内存交互的基本单位，一个页的默认大小是16KB
