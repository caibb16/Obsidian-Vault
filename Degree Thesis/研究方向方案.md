## 方向 A：业务感知 + 无线链路耦合的任务-节点映射

### 1.1 研究问题

多业务并发 LLM 推理在端-边-云异构节点上调度时，传统调度器只考虑算力与延迟，**没有把无线链路状态（SNR / RTT / 带宽 / 切换）和业务上下文局部性（KV 复用机会）一起作为决策信号**。这导致两个问题：

1. 链路质量差时仍把任务推到云端，引入额外 RTT
2. 业务上下文（KV cache）跨节点搬运时无差分压缩，浪费带宽

### 1.2 研究方法

**问题形式化**（建议三步走）：
1. **无线链路建模**：将无线链路状态建模为有限状态 Markov chain（FSMC），状态数取 3–5 阶（强/中/弱/切换/中断）
2. **业务到达建模**：不同优先级业务（XR / 具身 / 感知）建模为状态相关的 ON-OFF 过程
3. **联合优化目标**：构造 Lyapunov 漂移加惩罚函数
   $$\min \sum_t \Delta(Q_t) + V \cdot \mathbb{E}[\text{Delay} + \alpha \cdot \text{BandwidthCost} + \beta \cdot \text{KVReuseBenefit}]$$
   其中 Q_t 是任务队列积压、V 是控制参数

**算法设计**（三选一）：
- **Lyapunov drift-plus-penalty**（推荐入门）：给出确定性的最坏情况性能界
- **DRQN**（推荐进阶）：用深度循环 Q 网络处理部分可观测量
- **MARL**（推荐深入）：多节点之间分布式协作

**理论分析**：
- 收敛性证明（Lyapunov 方法）
- 复杂度分析（每决策步 O(N log N)）
- 性能下界（[O(1/V), O(V)] 的经典 drift-plus-penalty 结论）

**实验设计**：
- 基于 vLLM [PZ4JRSWC] / SGLang [BYH4SDXK] 扩展 KV scheduler
- 三类场景：XR 沉浸式 / 具身智能 / 动态感知
- 基线对比：Neurosurgeon [URU27SA3]、BanaServe [JNESFVG6]、HexGen-2 [J6LTZJPX] 简化版

## 方向 B：O-RAN xApp + LLM 推理节点联合调度

### 2.1 研究问题

当前 O-RAN xApp 调度（无线资源分配）和 LLM 推理节点选择是**分开的两套决策体系**：
- xApp 决策 RB 分配、调制编码
- LLM 编排器决策推理节点选择

二者各自独立优化，**可能冲突**：xApp 把 RB 分给某业务，但 LLM 编排器把该业务的推理放到远端云；反过来，LLM 想把推理推到边缘，但 xApp 分配的链路带宽不足。**目前没有"xApp 调度 + 推理节点选择"联合建模的工作**。

### 2.2 研究方法

**问题形式化**：
1. **xApp 状态空间**：RB 分配状态、QoS 测量、信道质量指示（CQI）
2. **LLM 编排器状态空间**：节点队列长度、KV 复用机会、模型位置
3. **联合决策空间**：xApp 选 RB 子集 + LLM 选节点对
4. **奖励函数**：共同最大化 QoS 满足率 + 最小化推理时延

**算法设计**（推荐 multi-agent RL）：
- xApp 端用 actor-critic（SZ2YMTG4 已验证）
- LLM 端用 PPO 或 SAC
- 训练方式：集中训练 + 分布式执行（CTDE）
- 收敛性证明：Stackelberg 均衡存在性

**理论分析**：
- Stackelberg 均衡存在性证明
- 纳什均衡与帕累托前沿分析
- 与单层决策的对比增益上界

**实验设计**：
- 在 O-RAN 仿真平台（如 OAI）+ LLM 仿真（如 vLLM）上联合仿真
- 真实业务场景：远程 XR 操控、机器人遥操作
- 对比基线：xApp 独立决策、LLM 独立决策

## 方向 C：KV 压缩感知的差分跨节点传输

### 3.1 研究问题

长上下文业务的 KV 在跨节点迁移时（如 HexGen-2 [J6LTZJPX]）**整块搬运，带宽代价大**。但已有工作证明：
- KIVI [UGVRS8CA]：KV 可 2bit 量化
- SnapKV [RZCFHBSX]：KV 有大量可丢弃 token
- H2O [W9EMGP53]：KV 有重尾重要性分布

**但这些压缩方案都是单节点内的，跨节点迁移时仍用全量 KV**。如果能基于重要性评估做差分传输，可以节省 50%-80% 带宽。

### 3.2 研究方法

**问题形式化**（基于信源编码）：
1. **重要性评估**：复用 H2O/SnapKV 的累积注意力分数作为重要性度量
2. **率失真上界推导**：在给定 RTT 预算下，求最大可传输 token 数量
3. **差分压缩**：仅传输"上次同步后新增的高重要性 token + 重要性分数的 delta"
4. **目标函数**：在精度损失 < ε 的约束下，最小化传输量

**算法设计**：
- **基于累积注意力的 token 重要性评估**（SnapKV 类）
- **基于率失真的传输策略**（信源编码理论）
- **基于 RDMA/RoCE 的直传优化**（工程实现）

**理论分析**：
- 率失真曲线推导
- 通信-精度权衡上界
- 传输开销 vs 推理精度的形式化

**实验设计**：
- 在 vLLM 引擎上扩展 KV scheduler
- 测试不同上下文长度（4K / 32K / 128K）
- 测量：传输量、端到端延迟、推理精度

## 方向 D：业务驱动的多模型协同推理编排

### 4.1 研究问题

AutoGen [7P8HPCH8] / AFlow [NYJUQSBN] / AutoMix [YN8AR7WI] 等多智能体框架**不感知无线环境**，业务编排决策可能把推理任务推到不合适的节点。具体而言：
- 工作流合成仅考虑任务依赖，忽略节点能力
- 模型路由仅考虑成本-质量，忽略链路状态
- 任务分解粒度不随上下文变化

### 4.2 研究方法

**问题形式化**：
1. **业务画像**：用 prompt 描述业务 QoS（延迟、精度、连续性）
2. **节点画像**：用结构化字段描述节点算力、显存、链路带宽、当前队列
3. **编排 prompt 模板**：将无线链路状态作为外部约束注入 LLM 编排 prompt
4. **验证机制**：AutoMix 风格的自验证

**算法设计**（LLM-as-agent）：
- 编排 LLM 接收业务请求 + 节点画像 + 当前链路状态
- 输出推理任务 DAG + 节点-任务映射
- 自验证模块检查是否满足 QoS 约束

**理论分析**（较弱，依赖经验）：
- 不同 prompt 模板的对比实验
- 不同业务类型的编排质量分析

**实验设计**：
- 基于 LangChain / AutoGen 实现编排器
- 接入 vLLM 作为推理后端
- 对比基线：无节点画像的编排、静态路由
